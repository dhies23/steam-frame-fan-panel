# sf-fan-qam — Steam Frame 快速设置菜单「风扇」页

> 这是**技术文档**，面向改代码的人。给测试者的安装 / 卸载 / 排错说明在上一层的
> `安装说明.md`。

在 Steam Frame（SteamOS + SteamVR GamepadUI）的 **快速设置菜单（QAM）** 底部标签栏里，
在「?」帮助气泡右边新增一个风扇图标标签，点开后是风扇转速控制与实时温度面板。

```
┌──────────────────────────┐
│  风扇                     │   ← 标题
│  风扇控制                 │
│   ✿  风扇转速   ────●──── │   ← 拖动滑杆 = 手动 PWM
│   ↻  自动温控        ●─── │   ← 开关：系统自动温控 / 手动
│   ◔  实时转速   4694 RPM  │
│   ◔  当前占空比      41 %  │
│  温度                     │
│   🌡 核心 SoC     54.8 °C │
│   🌡 CPU          54.4 °C │
│   🌡 GPU          53.2 °C │
│   🌡 内存         53.6 °C │
│   🌡 散热片       55.1 °C │
│   🌡 风扇口       52.9 °C │
└──────────────────────────┘
   🔔  ⚙  ⚡  🔋  ❓  ✿      ← 标签栏，风扇标签在「?」右侧
```

样式不是自己写的 CSS：面板里的每一行（滑杆行、开关行、分组标题、数值行）都是从
当前正在显示的原生 QAM 标签页里**克隆**出来的节点，所以外观、字号、间距、焦点
高亮都跟系统菜单完全一致，而且 Valve 更换哈希类名后依然有效。

## 组成

| 文件 | 作用 |
| --- | --- |
| `sf_fan_qam.js` | 注入到 QAM 页面的前端脚本，负责建标签、建面板、渲染数值、把拖动事件回传给守护进程 |
| `sf_fan_qamd.py` | 以 root 运行的守护进程：读温度/转速、写 `pwm1`、通过 CDP 注入上面的 JS |
| `sf-fan-qamd.service` | systemd 单元 |
| `../install.sh` | 一键安装（前置检查 + 安装后验证） |
| `../uninstall.sh` | 一键卸载（恢复系统温控 + 卸载后验证） |
| `../diagnose.sh` | 只读诊断，出问题先跑这个 |

## 安装

```bash
sudo ./install.sh
```

安装脚本会把三个文件放到 `/home/steamos/sf-fan-qam/`，单元放到
`/etc/systemd/system/sf-fan-qamd.service`，然后 `systemctl enable --now`，
最后等最多 15 秒确认守护进程真的注入进了 QAM 页面。

## 卸载

```bash
sudo ./uninstall.sh
```

它会停服务、把风扇交回系统温控、删掉单元和 `/home/steamos/sf-fan-qam/`，
然后**验证**原生控制器确实回来了（打印 `pwm1` 和转速）。

手工做的话等价于：

```bash
sudo systemctl disable --now sf-fan-qamd.service
sudo rm -f /etc/systemd/system/sf-fan-qamd.service
sudo rm -rf /home/steamos/sf-fan-qam
sudo systemctl daemon-reload
sudo systemctl start deckard-fan-control.service   # 确认系统温控已恢复
```

## 工作原理

SteamVR 的 GamepadUI 界面是 CEF 页面，`steamwebhelper` 开着
`--remote-debugging-port=8080`（只监听 127.0.0.1）。守护进程用标准库实现的
WebSocket 客户端连上 `valve.steam.gamepadui.barpopup` 这个 target：

1. `Runtime.enable` + `Runtime.addBinding("__sfFanSend")` —— 前端就能用
   `window.__sfFanSend(json)` 把指令发回守护进程；
2. 注入 `sf_fan_qam.js`（内容哈希变了才重新注入）；
3. 每秒钟 `Runtime.evaluate` 一次 `window.__SF_FAN__.setState({...})` 推新数据；
4. 收到 `Runtime.bindingCalled` 事件就执行指令。

前端 `sf_fan_qam.js` 用 `MutationObserver` 盯着 DOM，QAM 一出现就建标签和面板；
点风扇标签时把其它标签的 wrapper 隐藏、显示自己的面板。

有个细节值得说明：Valve 只在某个标签被选中时才渲染它的内容，所以如果 QAM 打开的
是「通知」这类没有任何滑杆/开关行的页面，就没东西可克隆。这时脚本会临时借一下
「设置」标签、等 React 渲染完、把行模板抓下来，再把用户原来的标签切回去；抓到的
模板同时存进 `sessionStorage`，这样下次整页重新加载后可以直接复用。存之前会校验
模板里的类名在当前样式表里还存在，Valve 换了哈希类名就会丢弃重抓。

## 硬件与安全

- 风扇 hwmon 名为 `slg4ax46073v`（`/sys/class/hwmon/hwmonN`），
  `fan1_input` 是每转 2 个脉冲，所以 `RPM = fan1_input / 2`；`pwm1` 是 0–100。
- 平时由 `deckard-fan-control.service`（root）按温度曲线自动控制。
- **手动模式会 `systemctl stop deckard-fan-control.service`**，此时只有本程序在写
  `pwm1`。PWM 被夹在 `MANUAL_MIN_PWM`–`MANUAL_MAX_PWM`（20–100）之间：
  这颗 Delta 风扇在 20 % 以下会失速，原生控制器的下限也是 30 %，所以任何情况下
  都不会写出 0（滑杆被隐藏/塌缩时读到的「0 %」曾经真的把风扇停掉）。
- 三重恢复保护：
  1. 面板上把「自动温控」打开 → 立刻 `systemctl start`；
  2. SoC 温度 ≥ `SAFETY_TEMP_C`（88 °C）→ 自动恢复系统温控并在面板上提示；
  3. 守护进程退出（含 `systemctl stop`）→ `cleanup()` 恢复；
     单元里还有 `ExecStopPost=systemctl start deckard-fan-control.service` 兜底。
- 停止服务时守护进程会调用前端 `teardown()` 把标签和面板从界面里移除，
  所以不会留下一个不刷新的死标签。

### 手动模式怎么保证「一直有效」

手动接管期间有两件事会悄悄把控制权抢走，守护进程的看门狗（每 3 秒一次）会把它们按回去：

- **原生控制器复活**：`deckard-fan-control.service` 只是被 stop，任何再次拉起它的
  东西（依赖、手工启动、其它工具）都会立刻按自己的曲线覆盖 `pwm1`。守护进程发现
  它 active 就再 stop 一次；同时 `set_manual()` / `set_auto()` 现在都会**确认**
  `systemctl` 真的生效（最多重试 4 次），不再发一次命令就当成功。
- **`pwm1` 被改回**：EC 或别的写入者改了寄存器时，守护进程把用户设定的值重新写回。

另外前端对「回弹」做了处理：守护进程每次推送都比用户的操作新，用户刚拖完/刚点完的
那一瞬间硬件回显还是旧值，如果直接照抄，滑杆和开关就会弹回去。所以前端会把自己的
改动保留 `PENDING_MS`（2.5 s）等硬件追上；开关则采用乐观更新，点一下立刻切换，
不等回显——之前「点了没用」正是因为它翻过去又被旧状态翻了回来。

### 开关的状态是怎么画出来的

原生开关的状态**不是**靠 `aria-checked` 表达的：样式表里没有任何 `[aria-checked]`
规则，旋钮的位置和轨道的蓝色完全由一个附加类决定：

```
._9Ql-oVe…yLrDAetGoWx0GYqA6ShfS ._1PQppcgkuXQAiFPar9AGi- { transform: translateX(16px) }
```

克隆出来的开关天生带着（或天生不带）那个类，改 `aria-checked` 在屏幕上毫无变化，
所以按钮看着像坏的。现在脚本会在抓模板时**对比一个开着的和一个关着的原生开关**，
把差出来的那个类记下来，之后每次渲染直接增删它；万一某个标签页里只有同一种状态的
开关，就退化成把「开着」和「关着」的节点各克隆一份来回换。缓存的模板也一并存这两个
克隆，所以 QAM 重开后仍然能正确显示。

光改类名还不够。旋钮是靠 `transform` + `transition: transform .2s` 动画过去的，
而**过渡动画只在页面真的在合成时才会推进**：QAM 没被看着的时候（VR 里 overlay
没举起来、或者面板被别的标签页顶掉）整个 popup 都被节流，过渡会一直停在
`running` 状态、永远保持旧值。表现就是「点了开关，类名变了，画面纹丝不动」。
所以脚本除了改类名，还会把这个开关的两个过渡关掉、把 `transform` 和轨道底色
直接写进行内样式（颜色是照着原生开关量出来的），这样无论合成器在不在跑，
样式引擎都会立刻应用。手动关掉伪元素 `::before` 的蓝色填充，避免和行内底色打架。

### 实时转速为什么是这个刷新率

面板上的转速已经不是瓶颈了。实测把风扇从 25 % 一步拉到 100 %：

| 环节 | 延迟 |
| --- | --- |
| 面板推数据到页面 | `POLL_INTERVAL` = 0.4 s |
| 页面渲染到像素 | 同一帧内 |
| **面板总开销** | **中位 0.58 s，最差 0.64 s** |
| 风扇控制器产出新读数 | **每 ~3 s 一次** |

也就是说界面上看到的新数字，最多比内核里的值晚 0.65 s；再快也没有新数据可显示。
`fan1_input` 大约每 3 秒才变一次，而且这 3 秒是**硬件**的节奏，不是我们的：

- 三个进程同时读同一个 `fan1_input`，看到的变化时刻完全一致（同一秒内的抖动是
  读到的先后），说明它是驱动里的一份缓存，不是每次读都去问芯片；
- 拿掉驱动的缓存也没用：`read_reg` 直接走 i2c 读寄存器，`dmesg` 里还有
  `slg4ax46073v: tach did not complete in expected period` —— 这颗 Silego
  SLG4AX46073V 的测速窗口本身就要几秒才完成一次；
- 数字也不是被四舍五入糊掉的：一个采样窗口内它稳定在 ±9 RPM 内抖动。

所以「更新略慢」是硬件测速窗口决定的。把 `POLL_INTERVAL` 调到 0.4 s 已经足够
（守护进程 CPU 占用 0.7 %），再调小只会增加 CDP 往返而没有新数据。

## 开发 / 调试工具

仓库 `tools/` 下的脚本通过 CDP 直接驱动界面来验证，不需要戴头显：

| 脚本 | 作用 |
| --- | --- |
| `dev_deploy.ps1` | scp 三个文件到设备并重启服务；`-Action stop/cycle/status` 测拆卸与重注入 |
| `sf_verify.py` | 完整验收：标签位置/尺寸、面板可见性、控件与实时数据、拖动真的改 `pwm1`、开关真的交回系统 |
| `sf_test_regress.py` | 针对两个实际故障的回归：开关每次都响应、手动设定 15 s 后仍在、拖到最左也不会变 0、屏幕上的数字确实在跟着硬件走 |
| `sf_test_toggle_visual.py` | 检查开关**看起来**真的切换了（旋钮位置 + 蓝色轨道），而不只是 `aria-checked` 变了 |
| `sf_refresh.py` | 打开 QAM、选中风扇标签、把面板 DOM 导出到 `shots/panel_dump.json` |
| `sf_test_controls.py` | 模拟拖动滑杆、点击开关，再读设备 `pwm1` 验证 |
| `sf_test_toggle.py` | 单独测「自动温控」开关的手动/自动切换 |
| `sf_test_reopen.py` | QAM 反复关闭/重开后标签与面板是否还在 |
| `sf_test_coldstart.py` | 清掉模板缓存 + 拆掉 UI，验证守护进程重新注入并从零重建 |
| `sf_compare_style.py` | 逐项对比风扇面板与原生设置页的几何/字体，确认风格一致 |
| `sf_syntax_check.py` | 用 CEF 自己的 JS 引擎解析脚本，语法错误当场暴露 |
| `tools/device/sfdrive.py` | 在设备上直接驱动面板（开 QAM、点开关、拖滑杆、读状态），不依赖本机的 python websocket |
| `tools/device/rpm_latency.py` | 把内核测速、守护进程推送、屏幕像素三个时间点对齐，量出端到端延迟 |
| `tools/device/tach_window.py` | 把转速拉高拉低，测风扇控制器本身多久才产出新读数 |
| `dump_toggles.py` | 导出原生开关的开/关两种 HTML，用来找状态类名 |
| `sf_probe_slider.py` | 打印原生滑杆的 CSS 变量，用来对齐克隆出来的控件 |
| `build_preview.py` + `render.ps1` | 用导出的 DOM 和 Valve 自己的 CSS，在本地 headless Chrome 里离线渲染面板截图 |

```bash
python tools/sf_verify.py             # 一键跑完所有验收项
python tools/sf_test_regress.py       # 两个已报故障的回归测试
python tools/sf_test_toggle_visual.py # 开关的外观是否真的切换
python tools/sf_refresh.py            # 抓最新 DOM
python tools/build_preview.py         # 生成 shots/preview.html
powershell -File tools/render.ps1 -Html shots/preview.html -Out shots/qam_fan.png \
    -Width 340 -Height 470 -Scale 3
```

设备上的工具（scp 到 `/tmp` 后用 sudo 跑，因为要写 `pwm1`）：

```bash

```

## 命令行

```bash
sudo python3 sf_fan_qamd.py --status        # 打印当前温度/转速/PWM
sudo python3 sf_fan_qamd.py --set-pwm 60    # 手动 60
sudo python3 sf_fan_qamd.py --auto          # 交回系统
sudo python3 sf_fan_qamd.py --interval 0.5  # 前台运行，刷新间隔 0.5s
```

## 日志

```bash
journalctl -u sf-fan-qamd.service -f
```

`inject -> <hash> (build <hash>)` 表示注入成功；
`command: set_pwm 70` 表示面板上的操作已经传到守护进程；
`removed injected UI` 表示停止时已经把标签摘掉了。
